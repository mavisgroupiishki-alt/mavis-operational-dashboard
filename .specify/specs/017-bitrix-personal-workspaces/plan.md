# План реализации: личные кабинеты Bitrix24

**Статус:** готов к реализации после регистрации локального приложения Bitrix24
**Дата:** 2026-10-29

## Решение

Кабинет остаётся частью MAVIS Operational Dashboard, но открывается в Bitrix24
как локальное приложение. В момент запуска сервер проверяет краткоживущий
Bitrix-токен через `user.current`, создаёт отдельную подписанную сессию и
вносит в неё только `portal`, `bitrix_user_id`, `role` и срок действия.
Данные сотрудника фильтруются на сервере до сериализации ответа.

Это не заменяет текущий парольный дашборд до полного перехода и не передаёт
webhook, токен запуска Bitrix или токен Jarvis в браузер.

## Порядок работ

1. **Основа входа Bitrix24.**
   - Добавить строго разрешённый домен портала, проверку launch payload и
     запрос `user.current` только с сервера.
   - Подписывать короткую HttpOnly-сессию отдельным секретом.
   - Роль `director` назначать исключительно по `BITRIX_DIRECTOR_USER_IDS`.
     Кандидаты: Виктория Клепицкая и Анна Жихарева.
   - Добавить тесты: неверный домен, неверный токен, подмена user ID,
     истёкшая сессия и роль руководителя.

2. **Read-only API личного кабинета.**
   - `me`: проверенная личность и роль.
   - `workday`: вчерашние звонки, успешные ≥60 секунд, задачи, просрочки,
     сделки без дел, качество заполнения источника и типа.
   - `team` и слушание Jarvis: только `director`.
   - Кэшировать по пользователю и дате коротко; не повторять тяжелые запросы
     к Bitrix при смене вкладок.

3. **Состояния, которые нельзя угадывать.**
   - Подключить SLA этапов только из выгрузки роботов/согласованной карты.
   - Подключить проверку реестра ИСО/СУОТ через выделенный read-only адаптер.
   - При отсутствии одного из источников вернуть статус источника, а не
     произвольную оценку или подсказку.

4. **Jarvis.**
   - Расширить уже существующий защищённый operations API параметром
     подтверждённого manager ID; не доверять ID из браузера.
   - Вынести триггеры оплаты в детерминированную проверку с цитатой и
     тайм-кодом, не влияющую на балл при отсутствии надёжного доказательства.
   - Открывать запись только через одноразовую серверно-проверенную ссылку
     для владельца звонка или руководителя.

5. **Интерфейс и выпуск.**
   - Сделать компактный раздел «Моя работа» в существующей визуальной системе
     и адаптировать для iframe Bitrix24.
   - Руководителям показать обзор команды и прослушку; менеджерам — только
     свой экран.
   - Прогнать тесты API, ручной запуск через Bitrix с менеджером и
     руководителем, отрицательный тест подмены ID и отказ Jarvis.

## Обязательная настройка Bitrix24

Администратор портала создаёт локальное приложение с URL запуска
`https://mavis-operational-dashboard.onrender.com/bitrix/launch` и передаёт
`APPLICATION_TOKEN` в защищённую серверную переменную
`BITRIX_LOCAL_APPLICATION_TOKEN`. URL запуска принимает его только вместе с
`AUTH_ID` и отклоняет несовпадение до обращения к Bitrix API. После первого
запуска я фиксирую Bitrix ID Виктории Клепицкой и Анны Жихаревой в
`BITRIX_DIRECTOR_USER_IDS`. До этого никто не получает директорскую роль по
отображаемому имени.

## Верификация

- unit: верификатор launch payload и доступы по роли;
- API: менеджер не получает данные другого `ASSIGNED_BY_ID`;
- API: руководитель получает командную сводку;
- API: ошибка Jarvis/SLA/реестра ограничена соответствующей карточкой;
- браузер: менеджер и руководитель открывают один URL из Bitrix и получают
  разные представления;
- журнал: в нём нет токенов запуска, webhook и расшифровок.
