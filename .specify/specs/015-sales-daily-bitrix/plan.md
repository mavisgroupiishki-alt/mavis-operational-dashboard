# Технический план: Ежедневный отчёт продаж из Bitrix

**Спека:** [spec.md](spec.md)
**Создан:** 2026-10-07

## Технологии

Существующие FastAPI, `BitrixClient` и vanilla JavaScript. Новый серверный агрегатор получает ограниченные списки лидов, сделок и CRM-активностей за один календарный день, а браузер только отображает нормализованный контракт.

## Архитектура

```text
Выбранный день
   └─ /api/sales-daily
        ├─ Bitrix leads + deals → источники, стадии, менеджеры, тип клиента
        └─ Bitrix call activities → направление, длительность, менеджер
                                      ↓
                            нормализованный отчёт / статусы доступности
                                      ↓
                 вкладка «Ежедневный отчёт» внутри «Продаж»
```

## API / Интерфейсы

- `GET /api/sales-daily?date=YYYY-MM-DD` — read-only дневной отчёт.
- Параметр обязан быть календарной датой в часовом поясе дашборда; неверный формат возвращает 400.
- Контракт включает `leads`, `deals`, `calls`, `availability`, `generated_at` и выбранную дату.

## Правила данных

- Лиды и сделки отбираются по `DATE_CREATE` в полуинтервале выбранного дня.
- Названия источников, стадий, менеджеров и типов клиентов берутся из существующего CRM metadata-контракта.
- CRM activity типа «звонок» считается по времени активности. Нераспознанные направление и длительность не интерпретируются как нули.
- Историческая воронка на конец дня не рассчитывается из текущего состояния карточек: для неё нужна отдельная подтверждённая история стадий.

## Риски

- Портал может хранить длительность/направление отдельных звонков нестандартно. Нормализатор покажет такие записи отдельно, без искажения итогов.
- Историческая воронка требует событий стадий; текущая стадия не будет представлена как архивное состояние.
- Bitrix может отвечать медленно. Запрос ограничен одним днём, выполняется параллельно и кэшируется кратковременно.

## Проверка конституции

- [x] Принцип I: все подписи показывают точный источник и дату данных.
- [x] Принцип II: Bitrix доступен только на сервере и только для чтения.
- [x] Принцип IV: частичная недоступность данных имеет явный статус.
- [x] Принцип VI: чтение ограничено одним днём и имеет краткий кэш.
