# Технический план: Архив ежедневного отчёта продаж

**Спека:** [spec.md](spec.md)
**Создан:** 2026-10-07

## Технологии

Используются существующие FastAPI, Bitrix read-only клиент и долговременное KV‑хранилище `Storage` (SQLite persistent disk или Supabase). Новых зависимостей нет.

## Архитектура

```text
Текущий день → Bitrix24 → онлайн-отчёт
                          ↓
                  после 00:10–00:59
                          ↓
                 immutable daily archive → Storage

Прошедшая дата → архив есть? → архивный отчёт
                              → нет → текущие CRM-данные + явное предупреждение
```

## Схема данных

- Ключ `daily_sales_archive:YYYY-MM-DD`.
- Значение: `report`, `captured_at`, `timezone`, `version`.
- Запись создаётся только при отсутствии ключа; последующие попытки возвращают исходную запись.

## API / Интерфейсы

- `GET /api/sales-daily?date=YYYY-MM-DD` сохраняет существующий контракт и добавляет `snapshot.mode`, `snapshot.captured_at`, `snapshot.message`.
- Внутренний серверный планировщик пытается сохранить вчерашний отчёт с 00:10 до 00:59 по часовому поясу дашборда.
- Интерфейс выводит режим данных над обеими подвкладками дневного отчёта.

## Надёжность и ограничения

- Приложение не создаёт платный Render Cron Job без отдельного подтверждения: такой job стоит от $1/месяц и не имеет доступа к существующему диску.
- Если веб‑сервис не работал в окно фиксации, архив не создаётся задним числом. При просмотре такой даты пользователь увидит честный live‑fallback, а не фиктивный исторический срез.
- Для гарантии снимка при остановленном веб‑сервисе позднее потребуется отдельный платный cron и долговременное удалённое хранилище.

## Проверка конституции

- [x] I. Source fidelity: режим и время происхождения данных передаются явно.
- [x] II. Read-only: Bitrix не меняется.
- [x] IV. Honest availability: пропущенный архив не выдаётся за исторический.
- [x] V. Durable configuration: архив сохраняется через `Storage`.
- [x] VI. Fast reads: прошлый день отдаётся без нового Bitrix-запроса.
