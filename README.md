# MAVIS Operational Dashboard v2

Полноценный web‑дашборд Mavis Group на FastAPI. Источник факта — Bitrix24; планы хранятся в приложении. Предназначен для постоянного офисного экрана и обычного доступа с компьютера/телефона.

## Что внутри

### Общий экран
- выручка ОП;
- оплачено;
- чистая выручка;
- закрытые акты;
- продажи;
- проданные продукты;
- закрытые продукты производства;
- ёмкость производства;
- менеджеры, эксперты и ключевые риски.

### Продажи / План‑факт ОП
Сохранена логика исходной таблицы:
- отчётный период;
- предыдущий период (2 предыдущих месяца);
- итог 3 месяцев;
- лиды;
- квалифицированные лиды;
- конверсии;
- сделки и сумма;
- продажи и выручка;
- средний чек;
- продукты в сделках;
- проданные продукты;
- средний чек продукта;
- конверсия продукта в продажу;
- оплачено;
- чистая выручка;
- 5 недель месяца: 1–7, 8–14, 15–21, 22–28, 29–конец;
- 4 группы источников;
- точные источники Bitrix;
- менеджеры;
- у каждого менеджера: группы источников + продуктовые категории;
- продуктовые категории;
- текущие стадии ОП.

### Производство
- закрытые акты: количество и сумма;
- новые продукты от ОП: количество и сумма;
- закрытые из переданных в периоде;
- конверсия новых в успех;
- средний чек;
- ёмкость по предполагаемой дате закрытия;

- базовая премия по справочнику;

- доля закрытых с актом;
- без изменений 7+ дней;
- зависшие;
- вернувшиеся в производство;
- продуктовая матрица;
- эксперты;

### Эксперты
Для каждого эксперта:
- закрыто шт. / BYN;

- средний срок;

- NPS;

### Зависшие / риски
- воронка зависших: количество и сумма;
- возврат в производство;
- просроченные предполагаемые даты;
- без изменений 7+ дней;
- зависшие с ожидаемой датой в выбранном периоде;
- просроченные зависшие;
- причины зависания: количество + %;
- причины возврата: количество + сумма + %;
- просрочка 1–7 / 8–14 / 15–30 / 30+ дней.

## Drill‑down
Практически каждое агрегированное число кликабельно. Справа открывается расшифровка до конкретных лидов / сделок / продуктов со ссылкой в Bitrix.

Фильтры drill‑down поддерживают:
- менеджера;
- группу источников;
- точный источник;
- продукт / продуктовую категорию;
- эксперта;
- стадию;
- причину зависания / возврата;
- неделю месяца;
- отчётный / предыдущий период.

## Планы
Планы можно задавать:
- общие;
- по менеджеру;
- по группе источников;
- по точному источнику;
- по продукту / категории;
- по эксперту.

`ADMIN_KEY` защищает изменение планов. Для просмотра можно дополнительно включить общий `VIEW_PASSWORD`.

## Realtime
1. Bitrix отправляет событие на `/api/bitrix/event`.
2. Приложение сразу инвалидирует текущий кэш.
3. Backend пересчитывает данные.
4. Браузеры получают SSE‑событие и обновляют экран без F5.
5. Дополнительно есть контрольная синхронизация раз в `REFRESH_SECONDS` (по умолчанию 60 секунд).

## Переменные окружения
Скопируй `.env.example` в `.env` для локального запуска.

Обязательные/рекомендуемые:

```text
BITRIX_WEBHOOK=https://.../rest/.../.../
TIMEZONE=Europe/Minsk
REFRESH_SECONDS=60
BITRIX_EVENT_TOKEN=<случайная длинная строка>
ADMIN_KEY=<ключ для изменения планов>
VIEW_PASSWORD=<общий пароль, можно оставить пустым>
DATA_DIR=./data
DEMO_MODE=false
```

Webhook Bitrix используется только backend'ом и никогда не отдается в браузер.

## Render
Проект готов к Blueprint‑деплою через `render.yaml`.

1. Положить проект в GitHub/GitLab/Bitbucket репозиторий.
2. В Render выбрать **New → Blueprint** и подключить репозиторий.
3. Render прочитает `render.yaml`.
4. Ввести секреты:
   - `BITRIX_WEBHOOK`
   - `BITRIX_EVENT_TOKEN`
   - `ADMIN_KEY`
   - `VIEW_PASSWORD` (если нужен)
5. После деплоя получится адрес вида `https://mavis-operational-dashboard.onrender.com` (фактический subdomain может отличаться, если имя занято).
6. В Bitrix настроить исходящие события на:

```text
https://<АДРЕС-RENDER>/api/bitrix/event?token=<BITRIX_EVENT_TOKEN>
```

Для постоянного офисного TV‑экрана лучше использовать постоянно работающий instance. У бесплатного Render web service есть режим spin-down при отсутствии активности.

### Persistent storage
`render.yaml` монтирует диск в `/var/data`. Там хранится SQLite с планами. При обычных redeploy планы сохраняются.

## Неподключенные метрики из ежедневной отчётности
Приложение показывает их в разделе «Планы и качество данных» как `нужен mapping`, а не подставляет выдуманные значения:
- количество допродаж;
- премия за допродажи;
- итоговая премия (пока допродажи не подключены);
- % переделок по вине эксперта.

Базовая премия по продукту и нормативные сроки уже подключены через справочник ежедневной отчётности.

## Render Free

Эта сборка специально настроена на Render Free:

- `plan: free`;
- persistent disk не используется;
- `DATA_DIR=/tmp/mavis-dashboard`;
- для предотвращения spin-down используйте UptimeRobot HTTP monitor на `/health` каждые 5 минут.

Важно: SQLite на Free Render является временным. После restart/redeploy сохранённые через интерфейс планы могут сброситься.
Факт из Bitrix при этом всегда загрузится заново. Для постоянного редактируемого хранения планов потребуется
вынести только таблицу планов во внешнее бесплатное хранилище либо Bitrix.

## Supabase — постоянное хранение ручных данных на Render Free

Да, Supabase решает проблему сброса планов после redeploy Render Free.

Через Supabase сохраняются:
- планы;
- комментарии к плиткам;
- ручной NPS;
- состав менеджеров и экспертов;
- критерии зависших;
- настройки приложения.

### 1. Создай проект Supabase

Создай обычный проект Supabase.

### 2. Создай таблицу

Открой **SQL Editor** и выполни файл `SUPABASE_SQL.sql` из корня репозитория.

### 3. Добавь в Render Environment

```text
SUPABASE_URL=https://xxxxxxxx.supabase.co
SUPABASE_KEY=<server secret/service-role key>
```

Ключ должен находиться только в Render Environment и **не должен попадать во frontend или GitHub**.

После redeploy открой:

```text
/health
```

В ответе должно быть:

```json
"storage": "Supabase"
```

Если Supabase временно недоступен, приложение использует локальный SQLite fallback, но постоянное хранение в этом режиме не гарантируется.
